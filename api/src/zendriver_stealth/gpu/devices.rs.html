1//! Device rows: tie a WebGL renderer string to a capability [`Tier`] and to a
2//! coherent WebGPU adapter, so one renderer drives both surfaces.
3//!
4//! `adapter_for_renderer` derives a WebGPU adapter (vendor + architecture)
5//! from the spoofed WebGL renderer string. Dataset-mapped, deterministic —
6//! NEVER randomized (WAFs hash the WebGPU fingerprint; a random/unknown value
7//! reads as a bot).
8//!
9//! Architecture tokens come from Dawn's `gpu_info.json`, normalized
10//! (lowercase, spaces→hyphens) — the scheme Chrome's WebGPU backend uses for
11//! `GPUAdapterInfo.architecture`. Validated: Apple M4 Pro → "metal-3";
12//! NVIDIA Turing → "turing" (MDN). Only confident model→µarch mappings emit a
13//! token; unrecognized models get "" — Chrome legitimately returns "" for
14//! unclassified GPUs, so empty is coherent and safe. A WRONG token reads as an
15//! unknown device to a fingerprinting WAF.
16

20/// One device's identity. Only what genuinely varies per device lives here;
21/// the capability values come from the device's [`Tier`].
22///
23/// `unmasked_renderer` is read both by this module's tests and by
24/// [`default_renderer`], which is what `push_webgl` falls back to when the
25/// caller pins no renderer of its own. The two `webgpu_*` fields are reference
26/// data only: `push_webgpu` derives its adapter through
27/// [`adapter_for_renderer`] rather than from a row. They are still the row's
28/// declaration of what that device's adapter *is*, so the tests assert the
29/// derivation agrees with them — the two must never describe different GPUs.
30#[allow(dead_code)]
31#[derive(Debug, Clone, Copy, PartialEq, Eq)]
32pub(crate) struct DeviceRow {
33    pub unmasked_vendor: &'static str,
34    pub unmasked_renderer: &'static str,
35    pub tier: Tier,
36    pub webgpu_vendor: &'static str,
37    pub webgpu_architecture: &'static str,
38    /// Lowercase substring that identifies this device in a renderer string.
39    /// Explicit and independent of `unmasked_renderer` / `adapter_for_renderer`
40    /// — matching must never be derived from the row's own reference string.
41    pub match_token: &'static str,
42    /// Extra lowercase substring that must *also* be present, or `None` when
43    /// `match_token` alone decides the row.
44    ///
45    /// Exists because one row needs two facts that are not adjacent in the
46    /// string. ANGLE puts the vendor first and the backend tag last —
47    /// `ANGLE (NVIDIA, … Direct3D11 …, D3D11)` — and the NVIDIA D3D11 tier is
48    /// selected by exactly that pair, so no single contiguous substring can
49    /// express it. Splitting the D3D11 rows on `Some("nvidia")` also keeps the
50    /// vendor test out of `device_for_renderer`, which stays a table sweep.
51    pub vendor_token: Option<&'static str>,
52    /// Architecture [`adapter_for_renderer`] must derive for this row to
53    /// match, or `None` when the substring tokens alone decide it.
54    ///
55    /// Exists because one row is scoped to a *GPU generation*, which no single
56    /// substring names: Intel Gen9 spans `HD Graphics 5xx`, `HD Graphics 6xx`
57    /// and `UHD Graphics 6xx`. Naming the generation instead of enumerating
58    /// its spellings is what keeps the capability-tier split and the WebGPU
59    /// architecture token reading from one classifier ([`intel_architecture`])
60    /// rather than from two lists free to drift apart.
61    pub arch_token: Option<&'static str>,
62}

218/// The device row assumed for a platform, used both when a persona pins no
219/// WebGL renderer at all and when the renderer it pins matches no shipped
220/// tier.
221///
222/// **The rule: pick a row whose renderer string real Chrome could report on
223/// that platform.** A renderer string is read beside `navigator.platform`, and
224/// the two have to be a pair Chrome can produce. Choosing the string needs no
225/// new hardware capture — only choosing new *capability values* would.
226///
227/// - macOS gets the Apple Metal row, which is both coherent and real hardware.
228/// - Windows gets the D3D11 row. ANGLE's D3D11 backend is what Chrome uses on
229///   Windows by default, so the renderer string, `navigator.platform`, and the
230///   capability values beside them all describe one ordinary Windows machine.
231/// - Linux gets the Intel Iris Pro 580 Vulkan row. ANGLE's Vulkan backend is
232///   what Chrome uses on Linux, so this is real hardware under the API real
233///   Linux Chrome runs — the same standing macOS and Windows already had.
234///   Linux used to get a SwiftShader row instead, which was honest but said
235///   "this machine has no usable GPU", something some fingerprinters weight on
236///   its own; capturing the tier is what retired that last fallback. What the
237///   Vulkan row cannot claim is generality: its numbers are this Iris Pro's
238///   under this Mesa build, not Linux's or Vulkan's (see
239///   [`Tier::VulkanMesaIntelIrisPro580`]).
240///
241/// **Which SwiftShader row, and why there are two.** SwiftShader's
242/// *capability values* are platform-independent; its *renderer string* is
243/// not. Measured on 2026-07-25: the same flag set probed on Ubuntu 24
244/// (Chrome 150.0.7871.114, GPU-less VM) reproduced the macOS capture exactly
245/// — 0 of 82 WebGL1 parameters differed, 0 of 130 WebGL2, extension lists
246/// identical in content and order, all 12 precision entries identical — while
247/// the renderer string differed in one token, because SwiftShader selects its
248/// JIT backend at build time and Chrome prints the choice:
249///
250/// - Linux: `SwiftShader Device (Subzero)`
251/// - Windows: `SwiftShader Device (Subzero)`
252/// - macOS: `SwiftShader Device (LLVM 10.0.0)`
253///
254/// That is one capability tier and two identity rows, which is why the split
255/// lives in [`DEVICES`] rather than in [`Tier`], and why it needed no capture
256/// and no table regeneration. Neither row decides a *default* any more, now
257/// that Linux resolves the captured Vulkan row above — but Subzero is still
258/// what a Linux persona lands on when it pins a SwiftShader renderer itself,
259/// so it has to stay the build real Linux Chrome prints.
260///
261/// Windows' entry there was previously **inferred** from the Linux
262/// measurement; it is now measured too. `cargo run -p zendriver --example
263/// probe_gpu -- swiftshader` on Windows 10.0.21996 (Chrome 150.0.7871.186)
264/// prints `SwiftShader Device (Subzero)`, confirming the guess. It no longer
265/// decides a *default* — `Win32` resolves the D3D11 row above — but it is what
266/// a Win32 persona gets if it pins a SwiftShader renderer, so the row it lands
267/// on still has to be the right build.
268///
269/// The rejected alternative for Windows was a D3D11 *string* with no D3D11
270/// *tier*, which is what shipped before the tier tables existed: it looks like
271/// ordinary hardware, but [`device_for_renderer`] returned `None` for it, so an
272/// Intel name was served above *Apple Metal's* numbers. Capturing the tier is
273/// what makes the D3D11 row honest rather than plausible-looking — the row's
274/// name and its numbers now come from the same probe. The earlier default was
275/// worse still, reporting the Apple Metal string itself under a Win32 or Linux
276/// `navigator.platform`, a pair Chrome cannot produce and which
277/// [`platform_skew`](crate::gpu::invariants::platform_skew) flagged on every
278/// launch.
279pub(crate) fn default_device(platform: Platform) -> DeviceRow {
280    match platform {
281        Platform::MacIntel => METAL_APPLE,
282        Platform::Win32 => NVIDIA_D3D11,
283        Platform::LinuxX86_64 => VULKAN_INTEL_IRIS_PRO_580,
284    }
285}

311/// Pick the device row a renderer string belongs to, by explicit
312/// [`DeviceRow::match_token`] — never by a key derived from a row's own
313/// reference string.
314///
315/// A row matches when the renderer contains its `match_token`, plus — where it
316/// declares them — its [`vendor_token`](DeviceRow::vendor_token) and the
317/// architecture its [`arch_token`](DeviceRow::arch_token) names.
318///
319/// First match in [`DEVICES`] order wins, so a specific row must be listed
320/// ahead of one it is a special case of. Three pairs depend on that:
321///
322/// - `"subzero"` before `"swiftshader"`, or every Subzero string would resolve
323///   to the LLVM row's identity. Both carry the same tier, so ordering decides
324///   the identity string alone — but that string is the whole reason the rows
325///   are separate.
326/// - The NVIDIA D3D11 row before the generic one. Here ordering decides the
327///   **capability values**, not just a name: the two rows carry different
328///   tiers, and the generic row's `match_token` alone would swallow every
329///   NVIDIA string. Getting this backwards serves an RTX its 4096 instead of
330///   its measured 4095, which is one `getParameter` call from being read.
331/// - The Intel Gen9 D3D11 row before the generic one, for the same reason and
332///   with the same consequence: a Gen9 machine would otherwise report
333///   `MAX_SAMPLES` 8 and 19 WebGPU features where it measures 16 and 16.
334///
335/// The remaining tokens (`"apple"` and the Iris Pro's Mesa device name) are
336/// disjoint from those and from each other, so their position is not
337/// load-bearing.
338///
339/// Six tiers ship today (SwiftShader, Apple Metal, D3D11 FL11+ in its NVIDIA,
340/// Intel Gen9 and catch-all forms, and the Intel Iris Pro 580 under Mesa), so
341/// `None` is
342/// still expected for the backends none of them covers — a desktop-GL renderer, a D3D9 string, or **any Vulkan
343/// device other than that one Iris Pro**. That last one is not a gap waiting
344/// to be filled by widening the token: ANGLE's Vulkan caps come off
345/// `VkPhysicalDeviceLimits`, so serving another Linux GPU this row's numbers
346/// would be exactly the wrong-backend pairing the tiers exist to prevent (see
347/// [`Tier::VulkanMesaIntelIrisPro580`]). A **feature-level-10** D3D11
348/// renderer does *not* answer `None`: ANGLE emits the same trailing `, D3D11)`
349/// tag at every feature level, so an FL10 string matches the D3D11 row's
350/// `match_token` and is served the FL11 numbers silently. Telling the two
351/// apart needs an FL10 capture to compare against, which nobody has taken.
352/// Callers that need a value
353/// regardless should reach for [`default_device`] explicitly rather than have
354/// one guessed here. Adding a tier means capturing it on that hardware, not
355/// inventing values for an existing row.
356pub(crate) fn device_for_renderer(renderer: &str) -> Option<DeviceRow> {
357    let r = renderer.to_ascii_lowercase();
358    // Derived once, from the same classifier that names the WebGPU adapter, so
359    // a renderer resolves the Gen9 capability tier exactly when it reports the
360    // `gen-9` architecture. Two lists would let those answers disagree.
361    let architecture = adapter_for_renderer(&r).architecture;
362    DEVICES.iter().copied().find(|d| {
363        r.contains(d.match_token)
364            && d.vendor_token.is_none_or(|vendor| r.contains(vendor))
365            && d.arch_token.is_none_or(|arch| arch == architecture)
366    })
367}

369/// The `UNMASKED_VENDOR_WEBGL` string Chrome reports beside an ANGLE renderer.
370///
371/// Chrome answers `Google Inc. (<X>)`, where `<X>` is the same vendor token
372/// ANGLE puts first in its own renderer string — so the pair is *derivable*,
373/// and a renderer the caller pinned can be answered by its own vendor instead
374/// of by whichever device row happened to match it.
375///
376/// That distinction is load-bearing now that one row covers many cards. The
377/// D3D11 row declares NVIDIA, but its [`DeviceRow::match_token`] deliberately
378/// matches every FL11+ D3D11 renderer, Intel and AMD included — because the
379/// capability values really are shared. Reading the *vendor* off the row too
380/// would serve `Google Inc. (NVIDIA)` beside an Intel renderer, a contradiction
381/// a page reads in one line. Measured before this existed: pinning
382/// `ANGLE (Intel, Intel(R) UHD Graphics 630 ... D3D11)` served exactly that
383/// pair, and silently, since a matched row raises no warning.
384///
385/// Returns `None` for anything not in ANGLE's format, leaving the caller to
386/// fall back to the device row — which is right for the default renderers,
387/// since each row's own string derives that row's own declared vendor (asserted
388/// in `every_row_derives_its_own_declared_vendor`).
389///
390/// The token ends at the first comma **or** closing paren, whichever comes
391/// first. ANGLE's usual string has both — `ANGLE (Apple, ANGLE Metal ...,
392/// Version ...)` — but the one-field form `ANGLE (Google)` has no comma, and
393/// splitting on the comma alone carried the paren into the token and answered
394/// `Google Inc. (Google))`.
395pub(crate) fn vendor_for_renderer(renderer: &str) -> Option<String> {
396    let inner = renderer.strip_prefix("ANGLE (")?;
397    let end = inner.find([',', ')']).unwrap_or(inner.len());
398    let vendor = inner[..end].trim();
399    (!vendor.is_empty()).then(|| format!("Google Inc. ({vendor})"))
400}

402/// Extensions that may be claimed even where the backend lacks them, because
403/// a synthesized stub is indistinguishable from the real object.
404///
405/// The bar is narrow, and both halves of it matter: the extension object must
406/// carry constants **and nothing else in the API may consume them**. An
407/// extension whose constants feed some other call is not inert, because the
408/// stub satisfies `getExtension` while that other call still fails — a
409/// contradiction the page reaches in one line.
410///
411/// [`WEBGL_debug_renderer_info`] qualifies in the strict sense that matters
412/// here: its two constants are consumed by `getParameter`, and the patch
413/// serves both of them from the tier profile, so the stub is backed all the
414/// way through.
415///
416/// `EXT_texture_filter_anisotropic` deliberately does **not** qualify, and was
417/// removed after being listed here: its constants are consumed by
418/// `getParameter` **and** `texParameterf`, and neither is table-served. On a
419/// backend without it, the claimed list named it, `getExtension` handed over a
420/// stub, and `getParameter(ext.MAX_TEXTURE_MAX_ANISOTROPY_EXT)` answered
421/// `null` with `INVALID_ENUM` — exactly the contradiction this rule exists to
422/// prevent. It is now claimed only where the backend really provides it, like
423/// every other functional extension.
424///
425/// [`WEBGL_debug_renderer_info`]: https://registry.khronos.org/webgl/extensions/WEBGL_debug_renderer_info/
426pub(crate) fn inert_stubs() -> serde_json::Value {
427    serde_json::json!({
428        "WEBGL_debug_renderer_info": {
429            "UNMASKED_VENDOR_WEBGL": 37445,
430            "UNMASKED_RENDERER_WEBGL": 37446
431        }
432    })
433}

443/// Map a WebGL `UNMASKED_RENDERER` string to a coherent WebGPU adapter
444/// (vendor + architecture). Architecture tokens are Dawn's `gpu_info.json`
445/// names normalized (lowercase, spaces→hyphens) — the scheme Chrome's WebGPU
446/// backend uses for `GPUAdapterInfo.architecture` (validated: Apple M4 Pro →
447/// "metal-3"; NVIDIA Turing → "turing" per MDN). Only confident model→µarch
448/// mappings emit a token; unrecognized models get "" (Chrome legitimately
449/// returns "" for unclassified GPUs, so empty is coherent and safe — a WRONG
450/// token reads as an unknown device to a fingerprinting WAF). Add families
451/// here as they're confirmed.
452///
453/// A software rasterizer answers empty for *both* fields, and is matched before
454/// any hardware family so it cannot fall through to the Intel catch-all — see
455/// the arm's own comment.
456pub(crate) fn adapter_for_renderer(renderer: &str) -> GpuAdapterInfo {
457    let r = renderer.to_ascii_lowercase();
458
459    // Software rasterizer: no vendor to report, and it must be answered before
460    // the hardware branches so it cannot reach the Intel catch-all below. It
461    // did reach it, which is the split this arm closes: a SwiftShader row was
462    // Linux's default and Windows' before either tier was captured (see
463    // `default_device`), so such a persona served SwiftShader's renderer to
464    // WebGL and an *Intel* adapter to WebGPU. A persona that pins a
465    // SwiftShader renderer itself still lands here on every platform, which is
466    // what keeps the arm load-bearing.
467    // Both JIT-backend rows go through it — the token is
468    // `swiftshader`, which each renderer string carries.

541/// Intel's integrated-graphics generation, as Dawn's `gpu_info.json` names it,
542/// from an already-lowercased renderer string. `""` for a model this cannot
543/// place, which is what Chrome itself answers for an adapter it does not
544/// classify.
545///
546/// Extracted from [`adapter_for_renderer`] because it now decides two things
547/// rather than one. It still names the WebGPU adapter's architecture, and it
548/// also selects the Gen9 capability tier in [`DEVICES`] (through that row's
549/// [`arch_token`](DeviceRow::arch_token)) — `MAX_SAMPLES` and the WebGPU
550/// feature list are read off the device on D3D11, so Intel Gen9 measured
551/// differently from the AMD part the generic tier was probed on. One function
552/// for both means a renderer cannot be served Gen9's numbers while reporting
553/// some other generation's adapter, or the reverse.
554///
555/// The token set is deliberately narrow. `gen-12-lp` names Iris Xe and `gen-9`
556/// the Skylake-through-Coffee-Lake `HD`/`UHD` 5xx and 6xx families; everything
557/// else — Arc, Gen11's `Iris Plus`, the bare `Intel(R) Graphics` the corpus is
558/// full of — stays empty, because a *wrong* architecture token reads as a
559/// device that does not exist where an empty one reads as an ordinary
560/// unclassified adapter.
561///
562/// It sorts by *marketing name*, which is not quite a die: no token here
563/// reaches the Gen9 parts Intel sold as `Iris` (`Iris Graphics 540`/`550`,
564/// `Iris Plus Graphics 640`/`655`), so those stay empty and ride the catch-all
565/// tier. Under-reaching is the safe direction, and the fix for that one is a
566/// D3D11 capture of such a part — see [`Tier::D3d11Fl11IntelGen9`].
567fn intel_architecture(renderer_lower: &str) -> &'static str {
568    if renderer_lower.contains("iris xe") || renderer_lower.contains("xe graphics") {
569        return "gen-12-lp";
570    }
571    match hd_family_number(renderer_lower) {
572        Some(500..=699) => "gen-9",
573        _ => "",
574    }
575}
576
577/// The `HD`/`UHD Graphics` family number, but only when it is three digits.
578///
579/// Counting the digit run is what keeps Broadwell off a tier measured on
580/// Skylake silicon. Gen9 spelled its families with three digits (`HD Graphics
581/// 520`, `UHD Graphics 630`) where Gen8 before it used four (`HD Graphics
582/// 5300`, `5500`, `5600`, `6000`), so a plain `hd graphics 5` prefix takes both
583/// generations and serves the older one values nobody measured on it. A
584/// four-digit model answers `None` and gets an empty architecture token, which
585/// reads as an ordinary unclassified adapter rather than as a device that does
586/// not exist.
587///
588/// One search covers both spellings, since `uhd graphics` contains
589/// `hd graphics`.
590fn hd_family_number(renderer_lower: &str) -> Option<u16> {
591    const TOKEN: &str = "hd graphics ";
592    let start = renderer_lower.find(TOKEN)? + TOKEN.len();
593    let digits: String = renderer_lower[start..]
594        .chars()
595        .take_while(char::is_ascii_digit)
596        .collect();
597    (digits.len() == 3).then(|| digits.parse().ok())?
598}
