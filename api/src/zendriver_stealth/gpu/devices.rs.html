1//! Device rows: tie a WebGL renderer string to a capability [`Tier`] and to a
2//! coherent WebGPU adapter, so one renderer drives both surfaces.
3//!
4//! `adapter_for_renderer` derives a WebGPU adapter (vendor + architecture)
5//! from the spoofed WebGL renderer string. Dataset-mapped, deterministic —
6//! NEVER randomized (WAFs hash the WebGPU fingerprint; a random/unknown value
7//! reads as a bot).
8//!
9//! Architecture tokens come from Dawn's `gpu_info.json`, normalized
10//! (lowercase, spaces→hyphens) — the scheme Chrome's WebGPU backend uses for
11//! `GPUAdapterInfo.architecture`. Validated: Apple M4 Pro → "metal-3";
12//! NVIDIA Turing → "turing" (MDN). Only confident model→µarch mappings emit a
13//! token; unrecognized models get "" — Chrome legitimately returns "" for
14//! unclassified GPUs, so empty is coherent and safe. A WRONG token reads as an
15//! unknown device to a fingerprinting WAF.
16

20/// One device's identity. Only what genuinely varies per device lives here;
21/// the capability values come from the device's [`Tier`].
22///
23/// `unmasked_renderer` is read both by this module's tests and by
24/// [`default_renderer`], which is what `push_webgl` falls back to when the
25/// caller pins no renderer of its own. The two `webgpu_*` fields are reference
26/// data only: `push_webgpu` derives its adapter through
27/// [`adapter_for_renderer`] rather than from a row. They are still the row's
28/// declaration of what that device's adapter *is*, so the tests assert the
29/// derivation agrees with them — the two must never describe different GPUs.
30#[allow(dead_code)]
31#[derive(Debug, Clone, Copy, PartialEq, Eq)]
32pub(crate) struct DeviceRow {
33    pub unmasked_vendor: &'static str,
34    pub unmasked_renderer: &'static str,
35    pub tier: Tier,
36    pub webgpu_vendor: &'static str,
37    pub webgpu_architecture: &'static str,
38    /// Lowercase substring that identifies this device in a renderer string.
39    /// Explicit and independent of `unmasked_renderer` / `adapter_for_renderer`
40    /// — matching must never be derived from the row's own reference string.
41    pub match_token: &'static str,
42    /// Extra lowercase substring that must *also* be present, or `None` when
43    /// `match_token` alone decides the row.
44    ///
45    /// Exists because one row needs two facts that are not adjacent in the
46    /// string. ANGLE puts the vendor first and the backend tag last —
47    /// `ANGLE (NVIDIA, … Direct3D11 …, D3D11)` — and the NVIDIA D3D11 tier is
48    /// selected by exactly that pair, so no single contiguous substring can
49    /// express it. Splitting the D3D11 rows on `Some("nvidia")` also keeps the
50    /// vendor test out of `device_for_renderer`, which stays a table sweep.
51    pub vendor_token: Option<&'static str>,
52}

170/// The device row assumed for a platform, used both when a persona pins no
171/// WebGL renderer at all and when the renderer it pins matches no shipped
172/// tier.
173///
174/// **The rule: pick a row whose renderer string real Chrome could report on
175/// that platform.** A renderer string is read beside `navigator.platform`, and
176/// the two have to be a pair Chrome can produce. Choosing the string needs no
177/// new hardware capture — only choosing new *capability values* would.
178///
179/// - macOS gets the Apple Metal row, which is both coherent and real hardware.
180/// - Windows gets the D3D11 row. ANGLE's D3D11 backend is what Chrome uses on
181///   Windows by default, so the renderer string, `navigator.platform`, and the
182///   capability values beside them all describe one ordinary Windows machine.
183/// - Linux gets the Intel Iris Pro 580 Vulkan row. ANGLE's Vulkan backend is
184///   what Chrome uses on Linux, so this is real hardware under the API real
185///   Linux Chrome runs — the same standing macOS and Windows already had.
186///   Linux used to get a SwiftShader row instead, which was honest but said
187///   "this machine has no usable GPU", something some fingerprinters weight on
188///   its own; capturing the tier is what retired that last fallback. What the
189///   Vulkan row cannot claim is generality: its numbers are this Iris Pro's
190///   under this Mesa build, not Linux's or Vulkan's (see
191///   [`Tier::VulkanMesaIntelIrisPro580`]).
192///
193/// **Which SwiftShader row, and why there are two.** SwiftShader's
194/// *capability values* are platform-independent; its *renderer string* is
195/// not. Measured on 2026-07-25: the same flag set probed on Ubuntu 24
196/// (Chrome 150.0.7871.114, GPU-less VM) reproduced the macOS capture exactly
197/// — 0 of 82 WebGL1 parameters differed, 0 of 130 WebGL2, extension lists
198/// identical in content and order, all 12 precision entries identical — while
199/// the renderer string differed in one token, because SwiftShader selects its
200/// JIT backend at build time and Chrome prints the choice:
201///
202/// - Linux: `SwiftShader Device (Subzero)`
203/// - Windows: `SwiftShader Device (Subzero)`
204/// - macOS: `SwiftShader Device (LLVM 10.0.0)`
205///
206/// That is one capability tier and two identity rows, which is why the split
207/// lives in [`DEVICES`] rather than in [`Tier`], and why it needed no capture
208/// and no table regeneration. Neither row decides a *default* any more, now
209/// that Linux resolves the captured Vulkan row above — but Subzero is still
210/// what a Linux persona lands on when it pins a SwiftShader renderer itself,
211/// so it has to stay the build real Linux Chrome prints.
212///
213/// Windows' entry there was previously **inferred** from the Linux
214/// measurement; it is now measured too. `cargo run -p zendriver --example
215/// probe_gpu -- swiftshader` on Windows 10.0.21996 (Chrome 150.0.7871.186)
216/// prints `SwiftShader Device (Subzero)`, confirming the guess. It no longer
217/// decides a *default* — `Win32` resolves the D3D11 row above — but it is what
218/// a Win32 persona gets if it pins a SwiftShader renderer, so the row it lands
219/// on still has to be the right build.
220///
221/// The rejected alternative for Windows was a D3D11 *string* with no D3D11
222/// *tier*, which is what shipped before the tier tables existed: it looks like
223/// ordinary hardware, but [`device_for_renderer`] returned `None` for it, so an
224/// Intel name was served above *Apple Metal's* numbers. Capturing the tier is
225/// what makes the D3D11 row honest rather than plausible-looking — the row's
226/// name and its numbers now come from the same probe. The earlier default was
227/// worse still, reporting the Apple Metal string itself under a Win32 or Linux
228/// `navigator.platform`, a pair Chrome cannot produce and which
229/// [`platform_skew`](crate::gpu::invariants::platform_skew) flagged on every
230/// launch.
231pub(crate) fn default_device(platform: Platform) -> DeviceRow {
232    match platform {
233        Platform::MacIntel => METAL_APPLE,
234        Platform::Win32 => NVIDIA_D3D11,
235        Platform::LinuxX86_64 => VULKAN_INTEL_IRIS_PRO_580,
236    }
237}

261/// Pick the device row a renderer string belongs to, by explicit
262/// [`DeviceRow::match_token`] — never by a key derived from a row's own
263/// reference string.
264///
265/// A row matches when the renderer contains its `match_token` and, where it
266/// declares one, its [`vendor_token`](DeviceRow::vendor_token) as well.
267///
268/// First match in [`DEVICES`] order wins, so a specific row must be listed
269/// ahead of one it is a special case of. Two pairs depend on that:
270///
271/// - `"subzero"` before `"swiftshader"`, or every Subzero string would resolve
272///   to the LLVM row's identity. Both carry the same tier, so ordering decides
273///   the identity string alone — but that string is the whole reason the rows
274///   are separate.
275/// - The NVIDIA D3D11 row before the generic one. Here ordering decides the
276///   **capability values**, not just a name: the two rows carry different
277///   tiers, and the generic row's `match_token` alone would swallow every
278///   NVIDIA string. Getting this backwards serves an RTX its 4096 instead of
279///   its measured 4095, which is one `getParameter` call from being read.
280///
281/// The remaining tokens (`"apple"` and the Iris Pro's Mesa device name) are
282/// disjoint from those and from each other, so their position is not
283/// load-bearing.
284///
285/// Five tiers ship today (SwiftShader, Apple Metal, D3D11 FL11+ in its NVIDIA
286/// and non-NVIDIA forms, and the Intel Iris Pro 580 under Mesa), so `None` is
287/// still expected for the backends none of them covers — a desktop-GL renderer, a D3D9 string, or **any Vulkan
288/// device other than that one Iris Pro**. That last one is not a gap waiting
289/// to be filled by widening the token: ANGLE's Vulkan caps come off
290/// `VkPhysicalDeviceLimits`, so serving another Linux GPU this row's numbers
291/// would be exactly the wrong-backend pairing the tiers exist to prevent (see
292/// [`Tier::VulkanMesaIntelIrisPro580`]). A **feature-level-10** D3D11
293/// renderer does *not* answer `None`: ANGLE emits the same trailing `, D3D11)`
294/// tag at every feature level, so an FL10 string matches the D3D11 row's
295/// `match_token` and is served the FL11 numbers silently. Telling the two
296/// apart needs an FL10 capture to compare against, which nobody has taken.
297/// Callers that need a value
298/// regardless should reach for [`default_device`] explicitly rather than have
299/// one guessed here. Adding a tier means capturing it on that hardware, not
300/// inventing values for an existing row.
301pub(crate) fn device_for_renderer(renderer: &str) -> Option<DeviceRow> {
302    let r = renderer.to_ascii_lowercase();
303    DEVICES.iter().copied().find(|d| {
304        r.contains(d.match_token) && d.vendor_token.is_none_or(|vendor| r.contains(vendor))
305    })
306}

308/// The `UNMASKED_VENDOR_WEBGL` string Chrome reports beside an ANGLE renderer.
309///
310/// Chrome answers `Google Inc. (<X>)`, where `<X>` is the same vendor token
311/// ANGLE puts first in its own renderer string — so the pair is *derivable*,
312/// and a renderer the caller pinned can be answered by its own vendor instead
313/// of by whichever device row happened to match it.
314///
315/// That distinction is load-bearing now that one row covers many cards. The
316/// D3D11 row declares NVIDIA, but its [`DeviceRow::match_token`] deliberately
317/// matches every FL11+ D3D11 renderer, Intel and AMD included — because the
318/// capability values really are shared. Reading the *vendor* off the row too
319/// would serve `Google Inc. (NVIDIA)` beside an Intel renderer, a contradiction
320/// a page reads in one line. Measured before this existed: pinning
321/// `ANGLE (Intel, Intel(R) UHD Graphics 630 ... D3D11)` served exactly that
322/// pair, and silently, since a matched row raises no warning.
323///
324/// Returns `None` for anything not in ANGLE's format, leaving the caller to
325/// fall back to the device row — which is right for the default renderers,
326/// since each row's own string derives that row's own declared vendor (asserted
327/// in `every_row_derives_its_own_declared_vendor`).
328///
329/// The token ends at the first comma **or** closing paren, whichever comes
330/// first. ANGLE's usual string has both — `ANGLE (Apple, ANGLE Metal ...,
331/// Version ...)` — but the one-field form `ANGLE (Google)` has no comma, and
332/// splitting on the comma alone carried the paren into the token and answered
333/// `Google Inc. (Google))`.
334pub(crate) fn vendor_for_renderer(renderer: &str) -> Option<String> {
335    let inner = renderer.strip_prefix("ANGLE (")?;
336    let end = inner.find([',', ')']).unwrap_or(inner.len());
337    let vendor = inner[..end].trim();
338    (!vendor.is_empty()).then(|| format!("Google Inc. ({vendor})"))
339}

341/// Extensions that may be claimed even where the backend lacks them, because
342/// a synthesized stub is indistinguishable from the real object.
343///
344/// The bar is narrow, and both halves of it matter: the extension object must
345/// carry constants **and nothing else in the API may consume them**. An
346/// extension whose constants feed some other call is not inert, because the
347/// stub satisfies `getExtension` while that other call still fails — a
348/// contradiction the page reaches in one line.
349///
350/// [`WEBGL_debug_renderer_info`] qualifies in the strict sense that matters
351/// here: its two constants are consumed by `getParameter`, and the patch
352/// serves both of them from the tier profile, so the stub is backed all the
353/// way through.
354///
355/// `EXT_texture_filter_anisotropic` deliberately does **not** qualify, and was
356/// removed after being listed here: its constants are consumed by
357/// `getParameter` **and** `texParameterf`, and neither is table-served. On a
358/// backend without it, the claimed list named it, `getExtension` handed over a
359/// stub, and `getParameter(ext.MAX_TEXTURE_MAX_ANISOTROPY_EXT)` answered
360/// `null` with `INVALID_ENUM` — exactly the contradiction this rule exists to
361/// prevent. It is now claimed only where the backend really provides it, like
362/// every other functional extension.
363///
364/// [`WEBGL_debug_renderer_info`]: https://registry.khronos.org/webgl/extensions/WEBGL_debug_renderer_info/
365pub(crate) fn inert_stubs() -> serde_json::Value {
366    serde_json::json!({
367        "WEBGL_debug_renderer_info": {
368            "UNMASKED_VENDOR_WEBGL": 37445,
369            "UNMASKED_RENDERER_WEBGL": 37446
370        }
371    })
372}

374/// vendor + architecture for the spoofed WebGPU adapter. `device` and
375/// `description` are always emitted empty by the patch (Chrome masks them).
376#[derive(Debug, Clone, PartialEq, Eq)]
377pub(crate) struct GpuAdapterInfo {
378    pub vendor: String,
379    pub architecture: String,
380}
381
382/// Map a WebGL `UNMASKED_RENDERER` string to a coherent WebGPU adapter
383/// (vendor + architecture). Architecture tokens are Dawn's `gpu_info.json`
384/// names normalized (lowercase, spaces→hyphens) — the scheme Chrome's WebGPU
385/// backend uses for `GPUAdapterInfo.architecture` (validated: Apple M4 Pro →
386/// "metal-3"; NVIDIA Turing → "turing" per MDN). Only confident model→µarch
387/// mappings emit a token; unrecognized models get "" (Chrome legitimately
388/// returns "" for unclassified GPUs, so empty is coherent and safe — a WRONG
389/// token reads as an unknown device to a fingerprinting WAF). Add families
390/// here as they're confirmed.
391///
392/// A software rasterizer answers empty for *both* fields, and is matched before
393/// any hardware family so it cannot fall through to the Intel catch-all — see
394/// the arm's own comment.
395pub(crate) fn adapter_for_renderer(renderer: &str) -> GpuAdapterInfo {
396    let r = renderer.to_ascii_lowercase();
397
398    // Software rasterizer: no vendor to report, and it must be answered before
399    // the hardware branches so it cannot reach the Intel catch-all below. It
400    // did reach it, which is the split this arm closes: a SwiftShader row was
401    // Linux's default and Windows' before either tier was captured (see
402    // `default_device`), so such a persona served SwiftShader's renderer to
403    // WebGL and an *Intel* adapter to WebGPU. A persona that pins a
404    // SwiftShader renderer itself still lands here on every platform, which is
405    // what keeps the arm load-bearing.
406    // Both JIT-backend rows go through it — the token is
407    // `swiftshader`, which each renderer string carries.
408    // Empty matches what the SwiftShader rows themselves declare, and is what Chrome
409    // answers for an adapter it cannot classify — the honest value for a
410    // rasterizer that has no hardware behind it at all. (On a real SwiftShader
411    // Chrome `requestAdapter()` resolves null and there is no adapter to read;
412    // the patch cannot synthesize that, so it decorates whatever adapter the
413    // host does resolve with a vendor that claims nothing.)
414    if r.contains("swiftshader") {
415        return GpuAdapterInfo {
416            vendor: String::new(),
417            architecture: String::new(),
418        };
419    }
420
421    if r.contains("nvidia") || r.contains("geforce") || r.contains("rtx") || r.contains("gtx") {
422        let arch = if r.contains("rtx 50") || r.contains("rtx50") {
423            "blackwell"
424        } else if r.contains("rtx 40") || r.contains("rtx40") {
425            "lovelace"
426        } else if r.contains("rtx 30") || r.contains("rtx30") {
427            "ampere"
428        } else if r.contains("rtx 20")
429            || r.contains("rtx20")
430            || r.contains("rtx 16")
431            || r.contains("gtx 16")
432            || r.contains("gtx16")
433        {
434            "turing"
435        } else if r.contains("gtx 10") || r.contains("gtx10") {
436            "pascal"
437        } else if r.contains("titan v") {
438            "volta"
439        } else {
440            ""
441        };
442        return GpuAdapterInfo {
443            vendor: "nvidia".into(),
444            architecture: arch.into(),
445        };
446    }
447
448    if r.contains("amd") || r.contains("radeon") {
449        let arch = if r.contains("rx 9") || r.contains("rx9") {
450            "rdna-4"
451        } else if r.contains("rx 7") || r.contains("rx7") {
452            "rdna-3"
453        } else if r.contains("rx 6") || r.contains("rx6") {
454            "rdna-2"
455        } else if r.contains("rx 5700") || r.contains("rx 5600") || r.contains("rx 5500") {
456            "rdna-1"
457        } else {
458            ""
459        };
460        return GpuAdapterInfo {
461            vendor: "amd".into(),
462            architecture: arch.into(),
463        };
464    }
465
466    if r.contains("apple") {
467        return GpuAdapterInfo {
468            vendor: "apple".into(),
469            architecture: "metal-3".into(),
470        };
471    }
472
473    // Intel + everything unrecognized → Intel (the common integrated default).
474    let arch = if r.contains("iris xe") || r.contains("xe graphics") {
475        "gen-12-lp"
476    } else if r.contains("uhd graphics 6")
477        || r.contains("hd graphics 6")
478        || r.contains("uhd graphics 5")
479        || r.contains("hd graphics 5")
480    {
481        "gen-9"
482    } else {
483        ""
484    };
485    GpuAdapterInfo {
486        vendor: "intel".into(),
487        architecture: arch.into(),
488    }
489}

1038        );

1040        // Both sides spelled out, so the measured numbers are visible here and
1041        // not only in the generated table.
1042        for (profile, vectors, components, combined) in
1043            [(&base, 4096, 16384, 212992), (&nvidia, 4095, 16380, 212988)]
1044        {
1045            let param = |k: &str| profile.params_webgl2.get(k);
1046            assert_eq!(
1047                param("MAX_VERTEX_UNIFORM_VECTORS"),

1049            );
1050            assert_eq!(
1051                param("MAX_VERTEX_UNIFORM_COMPONENTS"),
1052                Some(&GlParam::Int(components))
1053            );
1054            assert_eq!(
1055                param("MAX_COMBINED_VERTEX_UNIFORM_COMPONENTS"),
1056                Some(&GlParam::Int(combined))
1057            );
1058            // The relations that make these one fact rather than three: the
1059            // components are the vectors in scalars, and the combined total
1060            // adds the same 12 * 16384 of uniform-block storage on both tiers.
1061            assert_eq!(components, vectors * 4);
1062            assert_eq!(combined, components + 12 * 16384);
1063        }
